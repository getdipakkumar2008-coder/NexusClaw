## Sequencing
Foundation first (WP1–WP4 are independent and unit-testable), then the Gateway (WP5) so everything else has a home, then behaviour (WP6–WP9), then channels and UX (WP10–WP12), then hardening (WP13). The first demonstrable milestone ("M1") is: CLI → Gateway → fake provider → reply, with pairing and policy active, before any real channel or model.

## Rules for every WP
1. Spec in `docs/` first (or already there); tests with the code; `pnpm check:all` green.
2. Security-sensitive WPs (2, 3, 4, 5, 8) get a threat-model note in the PR and are listed for external review.
3. Update `docs/provenance/LOG.md`, and surface-budget if core grows.
4. No real credentials in tests; channels use mocks/recordings.

## Decisions made while starting Phase 1
- **SQLite driver:** `node:sqlite` (built in; no native build step). Requires Node >= 22.13 where it no longer needs a flag. `engines` updated accordingly. Revisit only if it proves unstable (ADR-0003 follow-up).
- **Event-log durability:** `synchronous=FULL` by default (spike 2); callers batch events per transaction.
- **Vault KDF:** scrypt (N=2^17, r=8, p=1), not Argon2id as docs/06 §6 said: Node 22 has no built-in Argon2id (it arrived in Node 24.7+) and the project avoids native dependencies. Parameters are stored in the (authenticated) header and bounded on read. Revisit when Node 24 is the floor.
- **Pairing:** a pairing code can only ever create a *guest*; owner identities are registered only via `registerOwner` from an authenticated local surface (T2). Challenge cooldown is tracked on the sender row so it survives code expiry (bug found by a test, fixed before release).
- **Gateway slice 1:** loopback-only (a non-loopback bind throws until TLS exists). Browsers can't drive it: Host must be loopback and Origin must be allow-listed (default none). One shared owner token (file mode 0600) authenticates local clients; per-address lockout after repeated failures. Method names may be single-segment (`status`) or dotted.
- **Sessions (WP6):** identified by (channel, conversation, scope); a provider only sees its own session's history. One run per session, extra inputs queue (default 20), at most 4 runs at once, 120 s timeout. After a restart, queued and running runs are marked failed (`interrupted by restart`), never silently replayed. Cancelled or failed runs store no assistant message. Deleting a session also deletes its events (so seq numbers can have gaps). Streaming deltas are coalesced into at most one event per 50 ms. The store's `inTransaction` now nests via savepoints and defers listener notification until the outermost commit.
- **Tools (WP8):** the executor is the only way tools run. Fixed order: known tool → strict argument validation → policy decision → approval (bound to the exact tool, arguments and caller, single use) → execution with timeout and cancel → audit event. Approvals are never awaited inside a call: the caller gets `approval_required` and retries with `approvalId` after the owner decides. Files: every path is canonicalised through the real file system and must lie in a workspace root; `.ssh`, `.gnupg`, `.aws` are never accessible and `.git` is read-only; symlinks and junctions cannot lead out; dangling symlinks are refused for writes; writes are atomic and refuse to replace a file unless `overwrite` is set. Exec: no shell (arguments are inert), the child gets a minimal environment (no API keys or tokens), stdout/stderr capped at 64 KiB each, and the whole process tree is killed on timeout or cancel. Tool outputs from files and commands are marked as untrusted so the caller can set the run's `tainted` flag. Known gap: a local attacker who can swap files between the path check and the open is out of scope (documented in `guard.ts`).
- **CLI and operations (WP12):** clients (`packages/cli`) talk to the Gateway only over the protocol and read the token from the data directory; server commands live in `src/daemon`, which also dispatches to the client commands so users see one binary. Errors print code, cause and fix, never a stack trace (`--json` for scripts; exit 2 = usage, 1 = failure). `setup` is idempotent and resumable; it never overwrites a config it cannot read. `doctor` checks Node version, data-dir and token permissions (POSIX), config validity/staleness, exposure, database integrity and schema, free disk, and port/Gateway state; `--fix` only does safe repairs (create dir, chmod, write defaults, migrate a stale config keeping `config.json.bak`) and never touches a file it cannot parse. `backup` uses SQLite `VACUUM INTO` (safe while running), records SHA-256 per file, re-verifies after writing, and deliberately omits the Gateway token; `restore` verifies first, refuses while a Gateway answers, and keeps the old database as `gateway.db.before-restore-*`. A lock file keeps one Gateway per data directory. Known gaps: the vault file name `secrets.vault` is a convention until vault wiring lands; backup is a directory, not an archive.
- **Model runtime (WP7 slice 1):** a model is an ACP harness started as a child process (`provider.harness` = claude | codex | cursor | gemini | custom; optional `command`, `args`, and `env` = names of variables to pass through). One harness process serves all Gateway sessions, started on first use and restarted after a crash; each Gateway session has its own harness session, and a rebuilt session gets a bounded recap of earlier turns. We advertise **no** file-system or terminal capability, answer the harness's permission requests through a policy hook that **rejects by default** and never picks an "always allow" option, and refuse every other request it makes. The harness gets a minimal environment (no API keys unless listed in `provider.env`) and runs in the workspace directory. `npx`-launched adapters are **pinned to exact versions** (supply chain); raising a pin is a deliberate edit. Replies are capped (1,000,000 characters); a harness that ignores cancel is killed after 3 s; errors carry a Fix line and are scrubbed of token-like strings. Windows: `.cmd` shims are never run through a shell with untrusted text (`npx` runs npm's own script with node; other shims only with plainly safe arguments). **Known gap:** whatever the harness does with its *own* built-in tools is bounded only by the permissions it asks for; until the tool bridge exists, treat a configured harness as able to read what its own login allows. Adding the optional `provider` key is not a breaking config change, so there is no migration.
- **Tool bridge (WP7 slice 2):** the harness is handed a stdio MCP server (ACP `session/new` `mcpServers`) that is this same binary run as `clawnexus mcp-bridge`; it connects back to the Gateway with a **per-session credential** and exposes the Gateway's tools (dots become underscores for MCP name rules). The Gateway decides everything; the bridge only translates and waits. Rules: (1) the credential allows only `tool.list`, `tool.call`, `approval.status`, as the session's principal, and cannot name another principal, session or trust level; (2) **every model-driven call is treated as tainted** (the model has read things we cannot see), so under the standard profile reads (R0) run, while writes, network and program execution wait for the owner, and the locked-down profile refuses program execution without a sandbox; (3) approvals are bound to the session (`agent:<session>`), the exact tool and arguments, single use, and at most 5 may wait per session (a hijacked model cannot bury the owner); (4) when a call needs approval the bridge waits up to 120 s while polling, so the model gets a real answer, and the owner sees `[approval needed] ...` with the exact command in the `chat` terminal or via `approvals list`; (5) credentials are in memory only, expire after 24 h and are revoked when the harness session ends or the Gateway stops; (6) the Gateway now applies the configured security profile to all tool calls (it was hard-wired to "standard"). **Harness permission shortcut:** Claude Code asks its client for permission before using *any* MCP tool; we answer "allow once" only when the request targets the MCP server we gave **that** harness session, whose name is random per session (`clawnexus-<12 hex>`), so a server of the same name in someone's own harness settings cannot ride on it; anything else, including the harness's own Bash/Edit tools, is still rejected. Only Claude Code's request format is recognised so far. **Known gaps:** a harness's own read-only built-ins may not ask permission at all (see the earlier gap); no sandbox backend; the owner decides approvals through the CLI only (no push prompt yet); a switch to turn tools off is an internal option because a config key would exceed `surface-budget.json` (needs an ADR to raise).
- **Plugin host (WP9 slice 1):** a plugin is a folder with `clawnexus.plugin.json`, installed under `<data>/plugins/<id>` and (optionally) a private `<data>/plugin-data/<id>`. **Install** copies and checks only: no links, at most 5000 files / 50 MiB, an ES-module entry inside the folder, a reserved-id list, SDK range; it runs nothing and enables nothing. **Enable** is bound to an *approval code* (hash of id, version, every file, and the permissions) shown by `plugins info`: if anything changed since the owner looked, enabling fails; if the code changes after enabling (update, tampering, a crash-restart), the plugin becomes `needs_approval` and is not started. **Isolation:** each plugin is its own Node process started with `--permission`: it can read only its own folder (and the shim), write only its data folder when the manifest has `"fs": ["data"]`, start programs/workers only with `"exec": true`, gets no environment from the Gateway (on Windows the OS adds its standard variables), and has a 128 MB heap cap. **Network is declared but not enforced** (Node has no network permission on the versions we support); the owner is told this at review time and a plugin with network or exec permission is rated at least R2 or R3. **Tools:** names are `<plugin-id>.<tool>` so they cannot shadow built-ins or each other; arguments are declared with a small typed spec and validated strictly by the host before the plugin sees them; the risk class is the plugin's declared class raised to a floor implied by its permissions (network R2, exec R3, data R1); output is always untrusted; descriptions are cleaned to one line and capped. **Supervision:** a crash is contained and reported, the plugin restarts with backoff (1 s, 2 s, 4 s) after re-verifying its code, and after more than 3 failures in 5 minutes it is marked `degraded` and left stopped; a call that outlives its timeout is cancelled and the process is ended if it does not wind the call down; results over 256 KiB, more than 8 concurrent calls, and log floods are refused or dropped. **Authority:** only the owner can manage plugins; the model's tool bridge can *use* plugin tools under normal policy but every `plugin.*` method is forbidden to it. **Known gaps:** no signatures or registry (trust is always `local-unsigned`); a local attacker who can modify files between the hash check and process start is out of scope; hashing happens on the Gateway's event loop (bounded by the size limits); plugin folders are not in `backup` yet; a plugin must not import packages from outside its folder at run time, so SDK helpers are used for types only or bundled; Node 22's permission flags are exercised only by CI.
- **Channels (WP10 slice 1):** `ChannelManager` is the only path from a platform to the model; adapters only call `host.deliver`. Pipeline, in this order: validate (strict schema, so an adapter cannot add fields such as a pre-made owner flag, and cannot name another channel: the router stamps the channel itself) -> per-channel flood guard -> clean the text -> **pairing** (unknown senders get a rate-limited code and never reach the model; the code goes only to that sender and is never written to the log) -> group rules (off / mention / all, optional group allow-list; a channel without group support ignores groups) -> **de-duplication** by platform message id, persisted so it survives restarts -> per-sender rate limit -> session -> run. A group session is always served at **guest** level. Sessions now record who they talk to (`principal`: owner or guest, schema v5) and the model's tool credential reads it **live** on every call, so demoting a sender takes effect immediately and a credential minted as guest can never rise. Messages from others reach the model labelled as untrusted (a courtesy only; policy decides what it may do). Replies go back only for runs the router started: a run started from the command line is never sent to a channel. Long replies are split at natural boundaries; sends are retried with backoff and a failure is recorded, never fatal; notices ("busy", "slow down", pairing prompt) are not repeated within 30 s. Adapter calls have timeouts, so a stuck platform cannot hold up others or shutdown.
- **WebChat:** a built-in channel (page at `/webchat`, socket at `/v1/webchat`, loopback only like the rest). A visitor's identity is derived from a 256-bit secret kept in their browser, so nobody can claim another visitor's id; strangers pair like on any channel. **The owner** is made only by a one-time link (`clawnexus webchat link`, minted over the authenticated local socket, valid 5 minutes, usable once, carried after the `#` so it never reaches logs or Referer headers). The socket accepts only the page's own origin (a web page on another site cannot connect); frames are strict; limits on connections per visitor and in total, a hello timeout, a 16 KiB frame cap and a per-connection rate limit apply. The page is served with a strict CSP (no inline script), shows all text with `textContent`, and has accessibility basics and light/dark themes. **Known gaps:** the page was exercised in a sandboxed script test and by a scripted client against a live Gateway, but not yet by eye in a real browser; no attachments; replies to a browser that is not connected are only in the history it sees on reconnect; there is no outbox, so a reply lost to a crash between completion and send is not re-sent; WebChat over a non-loopback address needs TLS first (SEC-6).
- **Always-ask rule:** R4 (irreversible/external side effects) is never auto-allowed by any profile.

## Exit criteria (from the roadmap)
Fresh machine → first reply in a paired channel ≤10 min (median, n≥5) · controls for T1–T3, T6, T7, T14, T15 implemented and tested · injection corpus passes · authz matrix + protocol conformance + crash-recovery tests pass · NFR footprint/latency met · external security review of policy/pairing/vault done · no known critical/high vulns.
